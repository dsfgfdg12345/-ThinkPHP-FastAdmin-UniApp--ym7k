Redis削峰、异步落盘与WebSocket实时推送实践
一、餐饮场景的流量特征与架构挑战
连锁餐饮平台面临典型的潮汐流量挑战——工作日午晚餐高峰、周末节假日、营销活动时，瞬时并发量可达平日3到5倍。针对小程序点餐平台的高并发场景（10万QPS、500万日订单、99.99%可用性），需要从接入层、服务层、数据层三个维度进行系统化改造。

接入层优化包括：CDN加速静态资源分发，商品图片等静态数据通过多地CDN节点分发；Nginx集群替代云LB实现负载均衡与限流，QPS超10万时丢弃请求；双线路容灾保障通信可靠性。服务层采用无状态服务容器化，服务端实例从十几台扩至100台，基础服务从虚拟机迁移至容器环境，支持弹性扩容。

二、Redis削峰与异步落盘机制
应对点餐洪峰的核心策略是“Redis削峰 + Lua防超卖 + 异步落盘”的组合方案。购物车与计算前置——用户的加购动作与复杂的满减、折扣逻辑计算全量在内存中快速完成；Lua脚本原子防超卖——针对限量秒杀或特价菜品，利用Redis Lua脚本保证库存检查与扣减的绝对原子性；异步落盘与削峰填谷——网关生成唯一订单号并快速响应前端后，将核心报文投递至消息队列，后端的订单微服务从容地拉取消息进行MySQL落盘。

订单服务与OMS通过消息队列异步同步，削峰且隔离故障影响；微信通知采用异步发送，进一步降低主流程的响应延迟。订单库按ID取模分4库，配合Sharding-JDBC路由；从库维持读写分离，硬件升级至16核32G配置。

三、WebSocket实时推送与多端状态同步
餐饮场景中，商户端需要实时接收新订单通知，用户端需要实时查看订单状态变化。传统的HTTP轮询方式在高并发下会造成大量无效请求。WebSocket长连接替代轮询方案，收银系统与小程序通过长连接接收实时推送（订单/取餐码），轮询频率从10秒降至1分钟保底。

当系统监测到某商户的连接离线时，会将待推送的新订单调度指令暂存至Redis的离线消息队列中；当商户端重连成功并完成鉴权的瞬间，系统自动推送积压消息，确保订单不丢失。源码搭建时，建议将WebSocket推送模块设计为独立的服务组件，通过事件总线与订单服务解耦，便于后续扩展和独立扩容。
